# First connection and repository handoff — 11 September 2026

## Objective and outcome

Connect the owner's Hantek DSO5102P directly to a Windows PC so an AI agent can
read its screen and perform basic acquisition control. The user later created
`C:\Github\Hantek` and asked to store all scope work there for other projects.

Live validation used Windows 11 Pro x64, Microsoft's WinUSB driver and Python
3.12 x64. Identification, echo, screenshot retrieval and acquisition stop/resume
worked on this particular scope. The scope was left acquiring in Auto mode.
This establishes USB/screen/control behavior, not measurement calibration or
safe connection to industrial equipment. No CNC endpoint was contacted.

## Findings retained for future work

1. Without a driver, Windows displayed `Gadget Serial v2.4`, problem 28.
2. The official Hantek driver had valid signatures but failed to load under
   Memory Integrity. Windows reported problem 39 and Code Integrity event 3111.
3. The Hantek application installer was downloaded/extracted, never executed.
4. Microsoft's inbox WinUSB driver solved the transport problem while Memory
   Integrity remained enabled. A dedicated interface GUID was registered.
5. Windows PowerShell 5 blocked the local script under its existing policy.
   The approved installation used PowerShell 7; no policy/security setting was
   weakened.
6. The first restart verification ran too soon, saw no device momentarily and
   reported failure after a successful binding. A later independent check
   confirmed WinUSB/problem zero. The helper now waits briefly for only that
   specific device to return and has offline tests for this behavior.
7. Stop acquisition produces additional short `0x92` replies. A strict initial
   screenshot reader failed on those messages. The repaired client tolerates
   only the observed short forms, records them, and still requires complete
   checksummed image data.
8. Initial interrupted screenshot transfers were retained. Their cleanup used
   bounded reads with no additional scope commands. They are not valid captures.

## Validation after relocation

All 15 Python checks and seven synthetic binding-helper checks passed. These
tests do not access hardware. The launcher also passed configuration and help
checks from a different working directory.

Live identification from `C:\` succeeded using the new repository launcher.
The first echo encountered a pending `0x92` status reply and correctly failed
its strict response check. A deliberate bounded read-only cleanup received 40
bytes in two reads and ended on the USB idle timeout. It sent no scope command.
The one-off recovery script and evidence are retained in
`.local/migration-check/`; they are historical diagnostics, not standard entry
points or an automatic retry mechanism.

After cleanup, a fresh echo succeeded and the relocated launcher saved
`artifacts/captures/scope-20260911T152345.014405Z.png` with complete image data and
validated checksums. Visual inspection showed Auto acquisition, CH1 1.00 V/div
and 800 us/div. No acquisition or other instrument-setting command was sent
during relocation validation. No driver was reinstalled.
